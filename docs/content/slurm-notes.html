The runtime plugin interface is new in Slurm 26.11. This page lists its properties and limits that have an effect on the operation of the plugin.

The plugin is for one Slurm version

The runtime interface is internal to Slurm. It is not a stable interface as SPANK is. Slurm loads a plugin of this type only if the plugin has the version of Slurm itself, the patch level included.

  • Build the plugin against the configured source tree of the Slurm version that you install.
  • Build it again for each Slurm update, also for a patch release such as 26.11.1.
  • The functions of the interface can change in a later release of Slurm. Then the plugin needs a change of its source.

At the time of this release of the plugin, Slurm 26.11 is a release candidate. The tests use the commit 85de8ed of the slurm-26.11 branch, which reports the version 26.11.0-0rc2.

Where Slurm loads the plugin

ProgramLoads the pluginFunction of the plugin
srun, sbatch, sallocYesOptions, input variables, variables of the job
slurmstepdYesStart of Apptainer for each task
slurmctld, slurmd, slurmdbdNo

Thus install the plugin and apptainer.conf on the submit hosts and on the compute nodes. The controller does not need them.

Make the plugin the default runtime

Slurm reads the options of a command before it knows the runtime that --runtime selects. If the plugin is not the default runtime, this has effects that can surprise a user:

  • srun --container=IMAGE --runtime=apptainer starts the task on the host. --runtime must be before --container.
  • sbatch and salloc refuse the --apptainer-* options after --runtime=apptainer.

With DefRuntimePlugin=runtime/apptainer in slurm.conf, these effects do not occur. See Select the runtime for the details and for the alternatives.

One runtime for each step

A step has one runtime plugin. If runtime/apptainer is the default, --container names an Apptainer image, not an OCI bundle. A user who wants the OCI runtime of Slurm selects it with --runtime=oci.

Trust

  • The plugin starts Apptainer as the user of the job, after slurmstepd dropped its privileges. A user gets no rights from the plugin that the user does not have in a job without a container.
  • The options of a job are data of the user. AllowUserArgs=no is a policy for the options of Slurm. It is not a security boundary: a user can start apptainer in a job directly. To restrict what containers can do, use the configuration of Apptainer itself.
  • apptainer.conf has the trust of slurm.conf. Only root must be able to write it.

Not tested

The end-to-end tests do not cover heterogeneous jobs, scrontab, slurmrestd, and architectures other than x86-64.
