The plugin runs in two places: in the commands on the submit host, and in slurmstepd on the compute node. This page shows how the options go from one to the other.

The image: a field of the request

Slurm has a container field in the job request and in the step request. The plugin writes the image there. Slurm then handles it like its own data:

  • slurmctld stores it in the job record. scontrol show job shows it.
  • slurmstepd gets it with the step, without a variable that a script can change.

The other options: variables of the job

The request has no fields for bind paths and arguments. The plugin writes them into the environment that the job gets, as SLURM_APPTAINER_BIND, SLURM_APPTAINER_ARGS and SLURM_APPTAINER_NO_DEFAULT_BINDS. On the node, the plugin reads them from the environment of the step.

This has two effects:

  • The steps of a job get the options of the job. srun in a job finds the variables and uses them as defaults, as it does with SLURM_NTASKS.
  • The values are data of the user. A job script can change them. This is by design: the plugin starts Apptainer as the user, with the rights of the user.

No shell

The plugin builds the argument list in C and calls execve(). It splits ExecArgs, GlobalArgs and --apptainer-args into words with the quoting rules of a shell, but it does not expand variables, patterns or commands. The command of the task and the environment go to Apptainer without change.
