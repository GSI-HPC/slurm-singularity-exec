An MPI program in a container starts with srun, as on the host. The plugin gives the tasks access to the PMIx server of the step.

Run an MPI program

$ srun --mpi=pmix -N 4 -n 128 --container=/images/app.sif ./mpi_app

The image must have an MPI library with PMIx support, for example Open MPI. The MPI library of the image must be able to speak to the PMIx version of the cluster. See the PMIx documentation for the versions that work together.

If MpiDefault=pmix is in slurm.conf, --mpi=pmix is not necessary.

How it works

For each step with PMIx, slurmstepd starts a PMIx server on each node. The server makes a socket and files, and the tasks find them with PMIX_* variables. For a task in a container, these files must be in the container at the same path.

  • The plugin makes one directory for each step in a container, in SlurmdSpoolDir. The user of the job owns it.
  • The PMIx plugin of Slurm puts its files there.
  • If the directory has files when a task starts, the plugin binds it into the container. A step without MPI gets no bind.
  • slurmstepd removes the directory at the end of the step.

You do not have to add SlurmdSpoolDir to Bind. The option --apptainer-no-default-binds does not remove this bind.

Tasks on the same node

Apptainer without the setuid starter puts each container into its own user namespace. This causes problems for the MPI transports that share memory between the tasks of one node. The Apptainer documentation refers to issue 769 for the details.

The argument --sharens of apptainer exec puts the containers that one parent process starts into one user namespace, with one mount of the image:

$ srun --mpi=pmix -n 64 --container=/images/app.sif --apptainer-args=--sharens ./mpi_app
  • It works with the plugin. slurmstepd is the parent process of all tasks of a step on a node, and the plugin starts Apptainer with no process between them. The tasks of one step on one node share the namespace. Two steps do not.
  • Use it for a job, not for the site. Do not put --sharens into ExecArgs. The tasks join the namespace of the task that started first. If that task ends before the other tasks start, the other tasks fail. An MPI program waits for all its tasks. A step with short, independent tasks does not.
  • It is not necessary with the setuid starter of Apptainer, which uses no user namespace.

Arguments that stop MPI

Some arguments of apptainer exec isolate the container from the job. Do not use them for an MPI step, in ExecArgs or in --apptainer-args.

ArgumentEffect on an MPI step
--cleanenvRemoves the PMIX_* variables. The task cannot find the PMIx server: PMIx_Init fails.
--containallIncludes --cleanenv, with the same effect.
--containGives the container a minimal /dev. The devices of a fast network are not there, unless you bind them.

Fast networks

The plugin adds no devices or libraries of the host to the container. If the MPI library needs them, for example for InfiniBand, add them with Bind or ExecArgs in apptainer.conf, or put the drivers into the image.
